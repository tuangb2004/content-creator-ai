**Trả lời:**

Đề tài khóa luận của em là **"Xây dựng nền tảng hỗ trợ sáng tạo nội dung sử dụng công nghệ AI"** (Content Creator AI). Đây là một ứng dụng web cho phép người dùng tạo ra các loại nội dung đa phương tiện bao gồm văn bản, hình ảnh và video thông qua việc tích hợp nhiều mô hình trí tuệ nhân tạo khác nhau.

**Mục tiêu chính** của đề tài là xây dựng một nền tảng tích hợp, nơi người dùng có thể truy cập và sử dụng nhiều công cụ AI khác nhau trong một giao diện thống nhất, thay vì phải sử dụng nhiều công cụ riêng lẻ như ChatGPT cho text, Midjourney cho image, và các công cụ khác cho video.

**Các tính năng nổi bật của hệ thống bao gồm:**

1. **Tạo văn bản với AI** - Sử dụng Google Gemini và Groq Llama để tạo các nội dung văn bản như caption, bài viết, script video
2. **Tạo hình ảnh với AI** - Sử dụng Stability AI SDXL và Pollination Nano Banana để tạo hình ảnh chất lượng cao từ text prompt
3. **Tạo video với AI** - Sử dụng Google Veo 3.1 để tạo video từ text hoặc hình ảnh gốc
4. **Hệ thống quản lý dự án** - Lưu trữ, tổ chức và quản lý các nội dung đã tạo
5. **Trang Inspiration** - Nơi cộng đồng chia sẻ và học hỏi lẫn nhau
6. **Hệ thống credit và thanh toán** - Tích hợp PayOS để mua credit
7. **Xác thực đa phương thức** - Email/Password, Google OAuth, Facebook OAuth, TikTok OAuth
8. **Hỗ trợ đa ngôn ngữ** - Tiếng Việt và Tiếng Anh
9. **Giao diện hiện đại** - Dark mode, responsive design

Dự án được phát triển tại Trường Đại học Tài nguyên và Môi trường Hà Nội, Khoa Công nghệ Thông tin.

Đối tượng người dùng mục tiêu của Content Creator AI bao gồm bốn nhóm chính:

**Thứ nhất - Content creators cá nhân:** Đây là nhóm người dùng chính bao gồm TikToker, YouTuber, Blogger, Instagrammer. Đây là những người cần tạo nội dung đều đặn với chi phí hợp lý. Theo thống kê, tại Việt Nam có hơn 1 triệu TikToker và YouTuber hoạt động thường xuyên, và con số này đang không ngừng tăng lên.

**Thứ hai - Doanh nghiệp vừa và nhỏ (SMBs):** Các doanh nghiệp cần tạo nội dung marketing nhưng không có đội ngũ sáng tạo chuyên nghiệp. Họ cần một công cụ đơn giản, hiệu quả về chi phí để tạo content cho các chiến dịch quảng cáo.

**Thứ ba - Freelancers:** Những người làm việc tự do trong lĩnh vực thiết kế đồ họa, copywriting, video editing cần công cụ hỗ trợ để tăng năng suất và đa dạng hóa dịch vụ.

**Thứ tư - Sinh viên và người mới bắt đầu:** Những người chưa có kinh nghiệm trong lĩnh vực sáng tạo nội dung, cần hỗ trợ từ AI để học hỏi và phát triển.

**Lý do chọn nhóm đối tượng này:**

Em chọn nhóm đối tượng này vì thị trường content creation đang tăng trưởng mạnh mẽ, ước tính đạt 104.2 tỷ USD vào năm 2026. Đồng thời, các giải pháp hiện tại trên thị trường có những hạn chế như:

- Chi phí cao (ChatGPT Plus $20/tháng, Midjourney $10/tháng)
- Giao diện phức tạp, khó sử dụng cho người mới
- Chưa hỗ trợ tốt tiếng Việt
- Phân mảnh công cụ (phải dùng nhiều app khác nhau)

Content Creator AI ra đời để giải quyết những vấn đề này.

## Câu 8: Hãy giải thích sơ đồ kiến trúc tổng thể của hệ thống?

**Trả lời:**

Kiến trúc tổng thể của Content Creator AI được thiết kế theo mô hình Serverless với ba layer chính:

**Layer 1 - Client (Browser)**
- React Frontend chạy trên trình duyệt
- Giao diện người dùng được xây dựng với Vite và Tailwind CSS
- Các trang chính: LandingPage, DashboardHome, AgentChat, Inspiration, Projects, Pricing

**Layer 2 - Firebase Services**
- Firebase Authentication: Xác thực người dùng (Email, Google, Facebook, TikTok)
- Cloud Functions: Xử lý business logic (19 functions)
- Firestore Database: Lưu trữ dữ liệu NoSQL
- Firebase Storage: Lưu trữ hình ảnh và video
- Firebase Hosting: Deploy frontend

**Layer 3 - External APIs**
- Gemini API (Google): Text generation và image analysis
- Groq API: Text generation với Llama model (miễn phí, nhanh)
- Pollination API: Image generation (Nano Banana - miễn phí)
- Stability AI: Image generation (SDXL)
- Veo API (Google): Video generation (Veo 3.1)
- PayOS: Thanh toán tại Việt Nam

**Luồng dữ liệu:** Người dùng → React App → Firebase Functions → AI APIs → Trả về → Firestore/Storage → Người dùng

## Câu 12: Firebase là gì và tại sao bạn chọn Firebase thay vì tự xây dựng backend?

**Trả lời:**

Firebase là Platform as a Service (PaaS) của Google, cung cấp các backend services sẵn có. Em chọn Firebase vì những lý do sau:

**All-in-one platform:** Firebase cung cấp đầy đủ các services cần thiết:

- Authentication cho xác thực người dùng
- Firestore cho database NoSQL
- Cloud Functions cho serverless logic
- Storage cho file storage
- Hosting cho deployment

**Serverless architecture:** Không cần quản lý server, tự động scale theo nhu cầu, giảm chi phí vận hành đáng kể. Em không cần lo lắng về việc cài đặt, cấu hình hay bảo trì server.

**Real-time support:** Firestore hỗ trợ real-time listeners, đặc biệt quan trọng cho các features như Inspiration feed, nơi người dùng cần thấy cập nhật ngay lập tức khi có bài đăng mới hoặc tương tác mới.

**Free tier:** Firebase có free tier đủ cho development và testing, giúp em tiết kiệm chi phí trong quá trình phát triển.

**Integration:** React + Firebase là combination phổ biến, có nhiều tutorials và examples, giúp em dễ dàng tìm kiếm tài liệu khi gặp vấn đề.

**Development speed:** Thời gian phát triển nhanh hơn nhiều so với tự xây dựng backend từ đầu. Thay vì phải viết code cho authentication, database, API endpoints, em có thể tập trung vào logic nghiệp vụ của ứng dụng.

## Câu 13: Sự khác biệt giữa Firestore và Realtime Database của Firebase là gì? Tại sao chọn Firestore?

**Trả lời:**

Firestore và Realtime Database đều là NoSQL databases của Firebase, nhưng có những khác biệt quan trọng:

**Về Data Model:**

- **Realtime Database:** Sử dụng Tree structure, dữ liệu lồng nhau sâu, khó query
- **Firestore:** Sử dụng Collections và documents, linh hoạt hơn, giống JSON, dễ tổ chức và mở rộng

**Về Querying:**

- **Realtime Database:** Query limited, phải denormalize data nhiều
- **Firestore:** Compound queries, indexing tốt hơn, range queries, hỗ trợ query phức tạp hơn

**Về Scalability:**

- **Realtime Database:** Scaling manually, có giới hạn
- **Firestore:** Auto-scaling, better performance ở scale lớn

**Về Pricing:**

- **Realtime Database:** Bandwidth-focused
- **Firestore:** Operations-focused, thường rẻ hơn cho read-heavy apps

Em chọn Firestore vì:

- Data model phù hợp với cấu trúc dữ liệu của dự án (users, projects, posts)
- Query capabilities tốt hơn cho features như filtering posts theo category, type
- Scaling tốt hơn cho future growth
- Đây là lựa chọn được Google khuyến khích cho các dự án mới

## Câu 14: Cloud Functions hoạt động như thế nào trong kiến trúc serverless?

**Trả lời:**

Cloud Functions là functions chạy trên cloud mà không cần quản lý server. Trong dự án này:

**Các Trigger types:**

- **HTTP triggers (onRequest):** Gọi từ frontend qua HTTP, thường dùng cho webhooks
- **Callable functions (onCall):** Gọi từ Firebase SDK, tự động handle authentication
- **Auth triggers (onUserCreate, onUserDelete):** Chạy tự động khi có user được tạo hoặc xóa
- **Pub/Sub triggers:** Chạy khi có message trong topic, dùng cho video queue processing

**19 Cloud Functions trong dự án:**

- generateContent: Text/Image generation với Groq, Gemini, Pollination, Stability
- generateVideo: Video generation với queue sử dụng Veo 3.1
- createPaymentLink, payosWebhook: Payment flow với PayOS
- createPost, getPosts, likePost: Inspiration CRUD operations
- saveProject, getProjects: Project management
- authTrigger: User initialization với 20 free credits

**Ưu điểm:**

- Pay-per-use: Chỉ trả tiền khi function được gọi
- Auto-scaling: Tự động scale theo số lượng requests

## Câu 22: NoSQL vs SQL? Tại sao chọn NoSQL (Firestore)?

**Trả lời:**

**SQL (Relational):**

- Tables với fixed schemas
- Relationships via JOINs
- ACID transactions
- Good cho structured data và complex queries

**NoSQL (Document):**

- Flexible schemas (JSON-like documents)
- Denormalized data
- Horizontal scaling

Em chọn NoSQL/Firestore vì:

1. **Flexible schema:** Projects có thể có different structures (text vs image vs video). NoSQL cho phép store tất cả trong same collection với optional fields.

2. **Real-time:** Firestore có built-in real-time listeners, perfect cho Inspiration feed.

3. **Serverless:** Firestore + Firebase = perfect match, auto-scale together.

4. **JSON-like:** JavaScript/React sử dụng JSON natively, no ORM needed.

5. **Query patterns:** App queries are simple (get by userId, get by category), don't need complex JOINs.

6. **Speed:** Read/write performance rất nhanh cho simple queries.

7. **Cost:** Pay-per-read/write, suitable cho projects with varying load.

## Câu 23: Bạn xử lý data denormalization trong Firestore như thế nào?

**Trả lời:**

Trong SQL, bạn JOIN tables. Trong NoSQL, bạn denormalize - store duplicate data để avoid joins và improve read performance.

**Ví dụ: posts collection**

Thay vì JOIN với users collection để lấy authorName mỗi khi hiển thị post, em store trực tiếp trong post document:

- authorId: để tham chiếu
- authorName: lưu trùng lặp (denormalized)
- authorPhotoURL: lưu trùng lặp (denormalized)

**Khi cần cập nhật denormalized data:**

Khi user thay đổi tên hoặc avatar, em sử dụng Cloud Function để cập nhật tất cả posts của user đó. Điều này đảm bảo dữ liệu luôn nhất quán mà không cần JOIN mỗi khi đọc.

**Subcollections vs root collections:**

- **Subcollections** (posts/{postId}/comments): Sử dụng khi dữ liệu luôn cần với parent - comments luôn cần postId
- **Root collections**: Sử dụng khi cần query độc lập - posts có thể query riêng biệt

## Câu 24: Firestore indexing và querying?

**Trả lời:**

**Indexing in Firestore:**

**Automatic indexes:** Firestore automatically creates indexes cho:

- Single field queries
- Equality (==) queries

**Composite indexes:** Cần tạo thủ công cho:

- Range queries (> < >= <=) combined with equality
- Order by with where
- Multiple where clauses

**Query patterns trong dự án:**

1. **Get user's projects:** Lấy tất cả projects của một user, sắp xếp theo thời gian cập nhật

2. **Get posts by category with pagination:** Lấy posts theo category, phân trang để tránh load quá nhiều dữ liệu

3. **Complex query:** Lọc posts theo category và số likes, sắp xếp theo likes

**Pagination:** Em sử dụng cursor-based pagination với startAfter() để load dữ liệu theo từng trang, tránh load quá nhiều data cùng lúc. Điều này giúp ứng dụng nhanh hơn khi có nhiều dữ liệu.

## Câu 25: Bạn xử lý migrations trong Firestore như thế nào?

Firestore migrations strategies:

**2. Cloud Function migration** (for data-wide changes):

Chạy một Cloud Function một lần để cập nhật tất cả documents trong collection. Ví dụ: Thêm field metadata cho tất cả projects nếu chưa có.

- Test on small subset trước
- Add version field để track migrations
- Run migrations incrementally cho large datasets

## Câu 26: Firestore transactions được sử dụng khi nào? Ví dụ?

**Trả lời:**

Firestore Transactions được sử dụng khi cần read và write multiple documents atomically - tất cả hoặc không có gì.

**Ví dụ: Trừ credit khi tạo nội dung**

1. Đọc user document để lấy số dư hiện tại
2. Kiểm tra xem số dư có đủ không
3. Trừ credit
4. Ghi lại vào database

Tất cả các bước này phải thành công hoặc thất bại cùng nhau. Nếu có lỗi ở bước nào đó, toàn bộ transaction sẽ được rollback, đảm bảo số dư luôn chính xác.

**Ví dụ khác: Tăng likes**

Sử dụng atomic increment để tăng số likes mà không cần đọc-ghi riêng lẻ, tránh race condition khi nhiều user like cùng lúc.

## Câu 33: Bạn có sử dụng Test-Driven Development (TDD) không? Ưu nhược điểm của TDD?

**Trả lời:**

Em không áp dụng TDD một cách nghiêm ngặt trong dự án này. Thay vào đó, em sử dụng approach "Test Last" - viết code trước, sau đó test để verify.

**Tuy nhiên, nếu áp dụng TDD, workflow sẽ là:**

1. **Red:** Viết test trước, thấy fail
2. **Green:** Viết code tối thiểu để pass test
3. **Refactor:** Cải thiện code

**Ví dụ TDD cho credit deduction:**

Đầu tiên viết test: Kiểm tra trừ credit đúng khi đủ, kiểm tra báo lỗi khi không đủ.

Sau đó viết code để pass test đó.

**Ưu điểm của TDD:**

- Code được thiết kế tốt hơn (testable)
- Regression prevention - Phát hiện bug khi thay đổi code
- Better documentation - Test như tài liệu
- Confidence to refactor - Tự tin khi sửa code
- Giảm bug từ đầu

**Nhược điểm:**

- Chậm hơn ban đầu
- Learning curve - Cần học cách viết test tốt
- Không phù hợp với exploratory work - Khám phá ý tưởng mới
- Over-engineering nếu áp dụng quá mức
- Không luôn feasible trong deadline constraints

## Câu 40: Code Coverage là gì? Mức coverage bao nhiêu là đủ?

**Trả lời:**

**Code Coverage** là tỷ lệ code được test, được đo lường bởi nhiều tiêu chí khác nhau.

**Types of coverage:**

- **Line coverage:** Lines of code được executed
- **Branch coverage:** Branches (if/else) được executed
- **Function coverage:** Functions được called
- **Statement coverage:** Statements được executed

**Coverage thresholds:**

- **0%:** No tests
- **50%:** Poor
- **70%:** Good (industry standard minimum)
- **80%:** Very good
- **90%:** Excellent
- **100%:** Ideal but often impractical

**For this project, recommended targets:**

- **Cloud Functions:** 80% (critical business logic)
- **React Components:** 70% (UI logic)
- **Utils/Helpers:** 90% (pure functions)

**Important:** Coverage ≠ Quality. Focus on testing critical paths and edge cases, không chỉ đơn thuần là đạt percentage cao. Một test tốt worth more than 10 shallow tests.

## Câu 43: Snapshot Testing là gì? Khi nào sử dụng?

**Trả lời:**

**Snapshot Testing** là phương pháp lưu snapshot của output, sau đó so sánh với các outputs trong tương lai để detect changes.

**When to use:**

- UI components (React components)
- JSON responses from APIs
- Error messages
- Configuration files

**When NOT to use:**

- Dynamic content (timestamps, random data)
- AI-generated content (non-deterministic)
- Large data structures

**Cách hoạt động:**

1. Chạy test lần đầu, Jest lưu snapshot vào file
2. Lần sau, so sánh output với snapshot đã lưu
3. Nếu khác nhau, test fail và hiển thị diff

**Updating snapshots:**

Khi thay đổi code dẫn đến UI thay đổi có chủ đích, chạy test với flag update để cập nhật snapshot.

**Best practices:**

- Commit snapshots
- Review snapshot changes carefully
- Keep snapshots small and focused

## Câu 46: Test Pyramids? Tỷ lệ các loại tests nên như thế nào?

**Trả lời:**

**Testing Pyramid** là mô hình kim tự tháp hướng dẫn tỷ lệ các loại tests:

```
           /\
          /E2E\           Few, expensive
         /─────\
        /Integration\    Some
       /───────────\
      /Unit Tests\   Many, cheap
     /────────────\
```

**Recommended ratios:**

- **Unit Tests:** 70%
- **Integration Tests:** 20%
- **E2E Tests:** 10%

**For this project:**

**Unit Tests (70%)** - Cloud Functions, utilities:

- Credit calculation functions
- Input validation
- Data transformation
- Prompt building

**Integration Tests (20%)** - API integrations:

- Firestore operations
- AI API calls
- Payment flow

**E2E Tests (10%)** - Critical user paths:

- Login flow
- Content generation flow
- Payment flow

**Why this ratio?**

- **Unit tests:** Fast, cheap, reliable, dễ viết và maintain
- **E2E tests:** Slow, flaky, expensive, khó maintain
- **Balance:** Good coverage với reasonable speed

## Câu 53: Security cho payment? Làm sao đảm bảo thanh toán an toàn?

**Trả lời:**

Payment Security được đảm bảo qua nhiều lớp:

**1. Signature Verification:**

Khi PayOS gọi webhook, verify signature bằng HMAC SHA256 để đảm bảo request thực sự từ PayOS, không phải kẻ giả mạo.

**2. Idempotency:** Prevent duplicate payments:

Kiểm tra transaction đã được xử lý chưa trước khi cộng credits. Nếu đã xử lý rồi thì bỏ qua, tránh trường hợp PayOS gọi webhook nhiều lần.

**3. HTTPS:** All payment communications over HTTPS

**4. PCI-DSS:** PayOS handles card data, we don't store sensitive info - Không lưu thông tin thẻ trong ứng dụng của em.

**5. Webhook verification:** Verify callback comes from PayOS, not fake requests

**6. Amount validation:** Verify amount matches expected - Kiểm tra số tiền thực tế khớp với expected.

## Câu 71: Tại sao chọn kiến trúc Serverless thay vì Server-based?

**Trả lời:**

**Server-based (truyền thống):**

- Cần quản lý server (EC2, VPS)
- Manual scaling
- Fixed cost (dù ít hay nhiều traffic)
- More operational overhead

**Serverless (Firebase):**

- Không cần quản lý server
- Auto-scaling theo demand
- Pay-per-use (tiết kiệm khi traffic thấp)
- Focus vào code, không phải infrastructure

**Why Serverless for this project:**

- Phù hợp với project có traffic không predictable
- Giảm thời gian dev (không cần backend setup)
- Free tier đủ cho development và testing
- Integration tốt với React frontend

## Câu 73: Firestore vs SQL Database - Khi nào chọn cái nào?

**Trả lời:**

**Chọn Firestore khi:**

- Data schema linh hoạt, có thể thay đổi
- Read-heavy workload
- Need real-time updates
- Simple queries (filter, sort)
- Scalability quan trọng

**Chọn SQL khi:**

- Data có cấu trúc cố định
- Complex queries với JOINs
- Transactions (ACID) quan trọng
- Reporting/Analytics (aggregations phức tạp)
- Data integrity quan trọng

**Trong dự án này:** Firestore phù hợp vì data models linh hoạt (project có thể là text/image/video), real-time cần cho Inspiration feed, queries đơn giản.

## Câu 97: Bạn đã handle memory leaks trong React như thế?

**Trả lời:**

**Memory Leak Prevention:**

Sử dụng cleanup function trong useEffect:

```javascript
useEffect(() => {
  const controller = new AbortController();
  
  const fetchData = async () => {
    try {
      const response = await fetch(url, { signal: controller.signal });
      const data = await response.json();
      setData(data);
    } catch (error) {
      if (error.name !== 'AbortError') {
        setError(error);
      }
    }
  };
  
  fetchData();
  
  // Cleanup
  return () => controller.abort();
}, [url]);
```

Điều này đảm bảo không có memory leak khi component unmount trong khi đang fetch.
